### Objective

The objective is to implement a majority voting system using the five models evaluated in TD1. We compare a fixed 2-of-3 panel with a 3-of-5 quorum across the 20 questions.

### Implementation

We completed the `vote_k_sur_n` method in `skeleton-multi-llm-en.py`.

The method:
- Accepts only executed proposals with a valid value.
- Requires a strict majority.
- Rejects duplicate model identities.
- Returns a consensus when a value reaches the required number of votes.
- Abstains when no value reaches the threshold.

### Synthetic Tests

All four synthetic examples were executed successfully.

|---|---|---|

| Disagreement | Abstention | No majority |
| Unavailable | Abstention | Insufficient votes |

The last example demonstrates that a majority vote does not guarantee a correct answer.

### Analysis of Changed Decisions

**C02 — Correct consensus becomes abstention**

The 2-of-3 panel returns 590320 cents with two votes from GPT-OSS-120B and Qwen. This matches the reference.

In the 3-of-5 quorum, the other models return 0, 135000, or an access error. Only two models agree on 590320, so the required threshold of three votes is not reached.

**C09 — Wrong consensus becomes abstention**

The 2-of-3 panel returns 0 cents with two votes from Cohere and Qwen. This is incorrect because the reference is 487980 cents.

In the 3-of-5 quorum, GPT-OSS-120B and GPT-OSS-20B both return 487980, while Cohere and Qwen return 0 and Dots returns 47900.

No value reaches three votes, so the system abstains.

### Additional Observation — C17

Both voting configurations abstain on C17.

GPT-OSS-120B and GPT-OSS-20B return the correct value of 258180 cents, but the fixed three-model panel contains only one of these models. Qwen does not provide an executed result.

The 3-of-5 quorum also abstains because only two models agree on the correct value.

### Conclusion

Increasing the number of models does not necessarily improve the number of consensus decisions.

The 3-of-5 quorum prevents the wrong consensus observed on C09, but it also abstains on C02, where the 2-of-3 panel had already found the correct answer.

This demonstrates the importance of selecting models carefully and defining an appropriate voting threshold.

### 3. The rule in one paragraph

The full one-page rule, with the cells of each line, is [`td2/C-routing/routing-rule-en.md`](../td2/C-routing/routing-rule-en.md). The family gives the level; the first route is the cheapest eligible route; every TD 1 route costs 0 USD, so ties go to the best TD 1 rate on the family, then to the **lowest** level. As a result, dots-3 (level 1, 6/6 and 4/4) answers F1 and F3 first, gpt-oss-20b (level 2, C10 and C18 correct) answers F2b first, and gpt-oss-120b (the only level-3 route) is kept for F2 and the combinations with F2. The check depends on the use: `none` only for an internal dashboard on a route at 100 % on the family; 2-of-3 for a customer on F1 and F3; reference for a customer on the age families; 3-of-5 then reference (F1, F3) or reference then human review (age families) for a payout. When the first route is unavailable: the next eligible route, then deferral if the request can wait and a refill is announced before the deadline, then the paid route gpt-oss-120b#openrouter (0.0006 USD per question) within budget, then abstention, never a silent fallback to a lower level.

### 6. Why the supplied `choose` prefers an available subscription to a deferral, and when to reverse it

**Exact reading of the branches.** `choose` tests four branches in a fixed order and returns in the first non-empty one:

1. `included = [r for r in eligible if r["available"] and r["cash"] == 0]`: run the `min` on `(allocation, level, id)`;
2. `waiting`: eligible, **not** available, `cash == 0`, `0 < reset_minutes <= deadline_minutes`, used only if `request["can_wait"]`: defer;
3. `paid`: eligible, available, `cash <= budget`: run the cheapest;
4. otherwise abstain.

A subscription has `cash == 0`, so it belongs to `included` whatever its `allocation`: allocation is not a filter, only the first sort key inside branch 1 (when both are available, the free route wins because its allocation is 0). When the free resource is exhausted and the subscription is available, branch 1 is not empty and returns `run` on the subscription: branch 2 is never evaluated, even when the free resource refills well before the deadline. Executed with the kit code (`td2/C-routing/outputs/priority-demo.jsonl`, line 1): small-free exhausted with a refill in 30 min, request that can wait 120 min, result `run senior-subscription`, cash 0.

**Why this order makes sense.**

- **No new spending either way.** The subscription fee is already paid; `allocation` is an accounting share of a fixed fee, not cash. Running now and deferring both cost 0 cash, and running now delivers 30 to 60 minutes earlier.
- **A refill time is a promise, not a fact** (Lecture 2). At wake-up the free route may still refuse: in TD 1 qwen3.8-27b received HTTP 429 on both attempts of C17 and C20, the retry budget ran out and the cells stayed `not_executed`. A deferral adds a queue, a second measurement and a second chance of failure; available capacity removes them.
- **Unused included quota is lost** at the end of its window. As long as the quota is ample, consuming it on a deferrable request has no opportunity cost.

**When the priority should be reversed.** When that last point is false, that is when the included quota has an opportunity cost. Operational condition: the request can wait, a free resource that is eligible for the family (TD 1 evidence) refills before `deadline_minutes`, and the subscription quota left in its current window is **not larger than the reserve** needed by the requests that cannot wait (urgent, high-stakes, or level-3 requests that only this resource serves) until the subscription's own reset. Spending the quota now would then push a later urgent request to the paid route (cash > 0) or to abstention: the deferrable request should wait for the free resource and the quota should be kept. The same holds when the subscription has a fair-use cap beyond which use is billed or throttled, since its allocation then turns into real cash. The free route's refill must be a measured pattern, not only an announced time, because a failed wake-up would delay the request twice. Executed in `td2/C-routing/priority_demo.py` (`choose_with_reserve`, which delegates to the kit `choose` otherwise): 5 requests left against a reserve of 8 gives `defer small-free, wake in 30 min`; 40 left gives `run senior-subscription`, as in the kit.

**Link with our rule.** Our six resources contain no subscription. The scarce capacity in our portfolio is the free quota of gpt-oss-120b#groq, the only level-3 route, and the same reasoning applies to it: among equally accurate free routes our `rank` takes the lowest level first, so F1 and F3 go to dots-3 and F2b to gpt-oss-20b, and the gpt-oss-120b quota stays available for F2 and its combinations, which no other free route can answer.

### 7. Limits and hypotheses

- Twenty questions support a batch-specific hypothesis, not a general error rate, a permanent ranking or a quorum error guarantee. F2b, F1+F2b, F1+F2 and F2+F3 rest on **one cell each**; F1+F2+F3 on two.
- One run per cell at temperature 0: no measure of run-to-run variability. A model version can change without notice.
- The level is "no wrong value on the families up to L": a single wrong value in a later batch would lower it. The rule must be recomputed (`td1_families.py`) on every new batch.
- gpt-oss-120b and gpt-oss-20b belong to the same family: in the 3-of-5 quorum their errors may be correlated.
- gpt-oss-120b#openrouter inherits the TD 1 evidence of the same model on Groq (portfolio: capability does not change with the route), but this route made no call in TD 1; it should be checked on our questions before carrying a customer figure without the reference check.
- dots-3-note-preview is a preview free route absent from the portfolio: it can disappear, and its mean latency in TD 1 was 2.8 s against 0.7 s for gpt-oss-20b. For an interactive use, the rule could put gpt-oss-20b first on F1 and F3 at the price of its quota.
- Availability states, refill times and the subscription quota figures of the demo are assumptions (simulation). The 2,000 / 500 token envelope over-estimates the measured TD 1 means (560 to 641 tokens in, 135 to 279 out).
- The reference check assumes that the question matches a validated family template; a question outside the eight families has no reference and no TD 1 evidence (*unknown capability*).
